# 已知问题

## 1. 测试会留下孤儿进程，导致应用静默打不开

**发现于**：2026-09-16，第 32 轮

**现象**
跑一次 `cargo test --workspace` 之后，会留下一个 `target/debug/jancode-manager`
进程，父进程变成 1（孤儿）。它占着单实例锁，此时启动**安装版** JanCode
只会记一条 `manager.already_running`，窗口不出现、无任何提示——
表现为「双击没反应」。

**实测证据**
```
跑测试前 jancode 进程数: 0
跑测试后: 1
  11357  target/debug/jancode-manager
```
对该进程查环境变量，确认它由测试启动：
```
CARGO_MANIFEST_DIR=.../crates/codex-plus-core
工作目录=.../crates/codex-plus-core
stdout → /private/tmp/t32.log   （继承自 cargo test）
```

**影响范围**
- 开发时：跑完测试后必须手动 `pkill -f jancode-manager`，否则安装版起不来
- 用户侧：不跑测试就不会遇到。但**同样的失败模式**（残留进程占锁 →
  静默不启动）在应用崩溃后同样会发生

**根因**
`codex-plus-core` 里有测试触发启动真实 manager 二进制（走
`install/mod.rs` 的 `Command::spawn()` 或 `update.rs` 的同类调用），
spawn 之后没有记录子进程、也没有在测试结束时回收。

**待办**
1. 定位到具体是哪个测试（本轮未定位完，已确认在 crates/codex-plus-core 内，
   且继承了 cargo test 的输出流）
2. 修法二选一：
   - 测试侧：spawn 后记录 Child 并 kill，或用 Drop guard 保证回收
   - 应用侧：单实例锁增加存活检测——持锁进程已死则接管，而不是静默退出
3. **应用侧那一条更值得做**：它同时修掉「崩溃后打不开」这个用户可见问题

## 2. 测试日志曾污染用户真实数据目录（已修）

**发现于**：2026-09-16，第 29–31 轮

已修复：测试进程自动重定向状态目录，并同步 `JANCODE_STATE_DIR`
环境变量让子进程继承。验证方式——跑完整个测试套件后诊断日志增量 = 0 字节
（修复前为 40KB）。

**遗留**：`~/.jancode/jancode.log` 里仍有约 2300 行历史测试记录混在
真实记录中，无法自动区分。这些是修复前产生的。新记录不受影响。
